# Offline compiled ETC1 mip chain

This diagnostic variant derives ten pre-encoded levels from the unchanged original 1024×1024 atlas. PNG, base PKM, material manifest and their original-art metadata are byte-identical to the frozen indexed candidate. No runtime encoder, image/model loader, extra asset lookup, engine dependency, or additional resource-manifest member is introduced. The generated bytes are compiled into the runner SO.

`provenance.json` pins the original PNG/PKM SHA-256 and the unmodified rg-etc1 source commit and file hashes. Both `rg_etc1.cpp` and `rg_etc1.h` retain their original Zlib license notices. The local CLI and Python generator use the encoder only during offline generation. The header contains the complete PNG and PKM SHA strings; the Python loader checks actual validated file hashes against both native queries, and the native enable API requires both exact strings and a current 1024-square ETC1 base.

The ten dimensions are 512, 256, 128, 64, 32, 16, 8, 4, 2 and 1. Compressed storage is `ceil(width/4) * ceil(height/4) * 8`, including eight bytes each for 2×2 and 1×1. Their unused texels remain outside the small image, as defined by Khronos OES_compressed_ETC1_RGB8_texture. The chain adds 174,776 resident GPU bytes. `build-report.json` binds every level, tool and generated header by SHA and records encoder checks. Native initialization independently checks all level dimensions, offsets, sizes and differential endpoints.

Regenerate with Python/Pillow and C++17, using a fresh explicit work directory outside runtime assets:

```sh
python -B runner/material_source/build_material_mips.py --atlas runner/assets/material_atlas.png --base-pkm runner/assets/material_atlas.pkm --output runner/native/runner_material_mips.h --work-dir /path/to/new-mip-build --compiler g++
```

On this Windows workspace, use an E: work directory and `--compiler D:/MinGW/bin/g++.exe`. The generator routes `TEMP` and `TMP` there and disables Python bytecode writes. An isolated regeneration matched the candidate header SHA `e093b7ce5d254286d311a2c014b12e5a7f26ce7bd2ac815aa4997fcc47e36c6e` exactly.

`INK_GL_MATERIAL_MIPS=0` is the default. Set it to `1` before Renderer/context creation to test the optional chain. The native API first creates a separate texture containing the validated base and every mip level. Only after all uploads pass does it enable `GL_LINEAR_MIPMAP_LINEAR` and commit the texture. Any failure deletes the incomplete candidate and retains the previous valid base with `GL_LINEAR`; Python reports a mip-specific fallback and keeps ETC1. Enabling needs an extra 512 KiB CPU mirror and one base reupload during setup; it does not encode or allocate per frame. New base/context operations reset level and resident-byte state, and destruction releases all textures/mirrors.

The Python renderer exposes requested/API state, enabled level count, extra resident bytes, upload attempts, actual successful transaction upload bytes and the mip-only fallback reason. Successful resident texture storage is 524,288 + 174,776 = 699,064 bytes. A successful transaction uploads another 699,064 bytes after the ordinary initial 524,288-byte base upload. The generated source remains an experiment until real Mali images and complete mapped performance pass.
